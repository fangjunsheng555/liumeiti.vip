# 旧用户会话迁移窗口

旧格式用户 Cookie 只在首次上线 v2 会话后的固定 14 天迁移期内兼容。活跃用户访问 `/api/auth/me` 时会收到新的、可撤销的 v2 Cookie；截止后仍持有旧 Cookie 的用户会得到中文“登录状态已过期，请重新登录”提示和清理 Cookie 的 401 响应。

## 推荐的生产配置

在首次部署前确定一个绝对截止时间，并在 Production、Preview 环境分别配置：

```dotenv
LEGACY_USER_SESSION_UNTIL=2026-08-18T12:00:00.000Z
```

该值必须是固定的 ISO-8601 时间，通常等于首次 v2 生产部署时间加 14 天。后续重新部署、冷启动或用户首次访问时都不要移动它。应用优先使用该变量，因此生产部署清单应在发布前校验它存在且可解析。

如果部署系统更适合记录首次部署时间，可改配：

```dotenv
LEGACY_USER_SESSION_DEPLOYED_AT=2026-08-04T12:00:00.000Z
```

应用会从该固定时间派生 14 天截止时间。不要同时依赖两个变量；两者同时存在时 `LEGACY_USER_SESSION_UNTIL` 优先。

## Redis 预初始化备选方案

无法使用环境变量时，部署步骤可在开始接流量前一次性写入绝对毫秒时间戳：

```text
SET lm:auth:legacy-user-until:v2 <absolute-unix-milliseconds> NX
```

应用运行时只读取这个键，不会在用户请求中创建或延期它。变量缺失且 Redis 锚点未初始化时，旧会话会返回 503；新格式会话不受影响。这一行为用于避免“首个旧请求”在部署数天后重新启动 14 天窗口。

## 发布校验

1. 将配置值解析为绝对时间，确认它等于计划中的唯一迁移截止时间。
2. 用一枚旧格式测试 Cookie 请求 `/api/auth/me`，确认截止前响应会换发 `lm_user` v2 Cookie。
3. 使用晚于截止时间的测试时钟确认响应为 401、中文提示要求重新登录，并清理旧 Cookie。
4. 重新部署后复查截止时间未改变。
